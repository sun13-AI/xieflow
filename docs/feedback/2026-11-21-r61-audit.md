### 1.2 真问题（P2）

**P2-1 成功体非 JSON → null 被当作 T 使用。** `apps/web/src/httpClient.ts:18` 与 `apps/web/src/authClient.ts:110`：
```ts
const data = (await res.json().catch(() => null)) as { error?: string } | null;
if (!res.ok) throw new Error(...);
return data; // res.ok 且 body 非 JSON 时返回 null
```
12 个页面 `getJson<T>`（`AssetsPage.tsx:35`、`ApprovalPage.tsx:89` 等）把返回值强转为 T，下游 `data.items`/`data.notifications` 会 null 解引用。当前服务端 Fastify 所有成功响应均带 JSON body（已核 `server.ts` 无 `.code(204)`），**未观测到真实触发**，故记 P2。
修法：`fetchJsonOrThrow` / `apiJson` 在 `res.ok && data === null` 时抛 `new Error("响应不是合法 JSON")`，不再返回 null。

**P2-2 离线队列 200 + 非 JSON 体仍清空队列。** `apps/web/src/OfflineStatus.tsx:105-115`：`res.ok` 分支无条件 `clearOfflineQueue()`，成功文案用 `data?.replayed ?? items.length`。若服务端返 200 但 body 不可解析，本地队列被清空却无法确认落库。同属低概率防御缺口，记 P2。
修法：`if (res.ok && data === null) throw new Error("同步响应不可解析")`；只有拿到明确 `replayed` 才清队列。

### 1.3 零问题证明
19 个空 catch 全有显式回退语句/注释（逐条见 1.1），不存在 `catch {}` 后继续执行且丢失错误上下文的路径；9 个 `.json().catch` 中 7 个在错误分支判空；31 条 `.then` 链无孤立未捕获分支；4xx/5xx 静默空态路径 0 条。

## 二、迁移健壮性（静态幂等 + 25 版本实测）

### 2.1 静态幂等检查
`packages/db/src/schema.ts` 共 27 个迁移（`version` 1→27 连续，`assertMigrationsConsistent` 校验通过）。

### 2.3 真问题（P2）

**P2-3 v22 中断窗口不可恢复。** 实测：构造 v21 库后人为执行到 v22 的 `ALTER TABLE fields RENAME TO fields_v21` 即中断（user_version 仍 21），再 `openDatabaseRaw` → 抛 `SQLite3Error: no such table: fields`，**库无法打开**（数据仍在 `fields_v21` 未丢）。根因：`runMigrations` 无事务包裹，v22 多语句重建中途失败后重跑会在 `ALTER TABLE fields RENAME` 处炸。触发条件为迁移执行期进程被杀/磁盘写失败，正常路径 25/25 通过，记 P2。
修法：把每个迁移的 `ensureColumns + up + PRAGMA user_version` 包在 `BEGIN IMMEDIATE … COMMIT/ROLLBACK` 中；或对 v22 加前置守卫——若 `fields_v21` 存在且 `fields` 不存在，先执行未完成步骤再继续。

### 2.4 零问题证明
v2–v26 共 25 档**真实构造旧 schema**（非仅改 user_version 的假样本），全部零崩溃、零数据丢失、重开零重复迁移；版本队列连续性由 `assertMigrationsConsistent` 断言锁定。
