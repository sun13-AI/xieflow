## 六、自曝（遗留问题，不阻塞收尾）

1. **未做真实多端双向 push/pull 前端编排**：本轮 UI 的「手动同步」按钮做真实 status/changes GET + 状态刷新，冲突选边调真实 POST apply；但客户端本地队列（离线积压变更）未做持久化，刷新页面后未同步计数以服务端 change_log 为准。
2. **`detectConflict` 的 merged 对真冲突默认取远端**（服务端 wins），UI 弹窗提供选本地/选远端；未做字段级混合（同一条里 title 取本地、status 取远端需用户分字段点选）——当前选边是整实体级。
3. **`change_log.payload` 存的是整实体字段快照而非 delta**：增量拉取按 id 游标幂等，但载荷体积随字段数增长；大实体场景建议后续做 delta 压缩（规则仍留 shared）。
4. **`applySyncChange` 的幂等判定限于「期望版本恰好落后一代 + 操作相同 + 载荷逐字节相等」**：更老的重复请求仍按 409 处理（给了冲突信息而非静默吞掉），这是刻意选择，避免误吞真正的历史冲突。
5. **没有 per-device / per-client 标识**：`user_id` 记录操作者，但同一账号多设备并行改动只能靠乐观锁串行化；设备维度留 M10 离线模式评估。
6. **无变更清理 / 压缩任务**：change_log 随使用线性增长；生产部署需加保留窗口（属运维策略，不在任务单）。
7. **越权防护只在 remote 模式对「记到别人名下」生效**：local 模式匿名可用（与既有业务路由口径一致）；公网部署应配合环境固定模式。
8. **截图 01~07 为钉态**：真实 HTTP 行为由 audit 的 scratch DB 独立锁定，仓库 `data/xieflow.db` 未被本轮写入。
9. **未做 CRDT 实时协同**：按任务单「最后写入 wins + 冲突提示」交付，实时协同留 M10 前评估。
10. **三平台 CI / unix pwsh 7 分支未实跑**：shot.ps1 新增段全 ASCII、PS5.1 Parser 0 错误；本机 Windows 限制，属 lead 发版环节。
11. **`docs/plan.md` 记账未改**：路线图记账 / 版本 / tag / push / Release 属 lead 收尾职责（宪法第二、五条），本轮严格未触碰。
