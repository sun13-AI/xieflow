### 真漏洞（交 yanfa 修）

#### P0-1 · 开放注册 + 零资源归属 = 匿名可获取全工作区读写（含删除他人数据）

- 证据：`server.ts:397-400` 把 `/api/auth/register` 列为公开；`:3648-3656` 注册无审批/无邀请码；`packages/db/src/index.ts:2985` 首个用户 admin、后续一律 `user`；上表 22 条资源路由零 owner 校验；`schema.ts` 业务表无 `user_id/owner`。
- 复现（scratch remote 模式实测，2026-11-21）：
  1. `POST /api/auth/register {"username":"m_admin","password":"AuditPass123!"}` → 201 `role=admin`；登录取 token。
  2. `POST /api/documents {"title":"admin-secret-doc"}`（admin token）→ 201 `id=1`。
  3. `POST /api/auth/register {"username":"m_user","password":"AuditPass123!"}` → 201 **`role=user`**（匿名即可自助获得合法身份）；登录取 token。
  4. `GET /api/documents/1`（user token）→ **200**，返回 admin 的文档。
  5. `DELETE /api/documents/1`（user token，无 body）→ **200 `{"deleted":true,"soft":true}`**；admin 再 GET → 404。同法 `DELETE /api/projects/1`（user token）→ 200。
- 建议修法：①remote 模式关闭公开注册或改为 admin 审批/邀请码（`user:manage` 保护 `/api/auth/register`）；②若确认"单工作区共享"是产品语义，至少给写/删操作加 admin 权限或按 `members.user_id` 建立资源归属并在服务层统一 `assertCanAccess(user, entity)`；③补 HTTP 断言：普通 user 读写/删他人资源必须 403/404，开放注册必须 403/409。

#### P0-2 · r49 备份恢复可改写 `settings.server.mode`，重启后 remote 静默降级为 local、全量鉴权消失

- 证据：`backup.ts:34` `settings` 在可恢复白名单内；`server.ts:4672-4679` export 与 `:4704-4722` restore 对任意登录用户开放；`server.ts:379-384` 启动时 `getSetting("server.mode")` **覆盖** `ENV_MODE`；`:443-452` local 模式跳过除三条探针外全部鉴权。
- 复现（scratch，两次进程均设 `XIEFLOW_MODE=remote`）：
  1. 以普通 user token `GET /api/backup/export` → 200（38 表）。
  2. 将 `tables.settings` 中 `{key:"server.mode", value:"remote"}` 改为 `"local"`。
  3. `POST /api/backup/restore {"backup":<篡改备份>,"confirm":"RESTORE_WORKSPACE"}`（同一 user token）→ **200**。
  4. 停服务、用**同一 DB 且仍设 `XIEFLOW_MODE=remote`** 重启：`GET /api/health` → **`mode=local`**；匿名 `GET /api/documents` → **200**（读到数据）；`GET /api/auth/guard` 仍 401（唯一保留的探针）。
- 建议修法：①`POST /api/backup/restore` 加 `assertPermission(user.role, "user:manage")`（或新增 `backup:restore` 权限）；②把 `server.mode` 从可恢复 `settings` 中排除（新增运行时表白名单，与 users/sessions 同级），或启动时只信 `ENV_MODE`、DB 中 mode 仅作 UI 提示；③恢复后若模式发生变化立即刷新内存 `serverMode` 并要求重新认证；④补变异红相断言：篡改 mode 的备份必须 422，重启后 remote 不降级。

#### P1-1 · 审批人身份由请求体声明，任意用户可冒充当前审批人通过/驳回/转交

- 证据：`server.ts:3399-3410` 把 `body.actor` / `body.actorMemberId` 直接传给 `store.actOnApproval`；`packages/db/src/index.ts:2705-2717` 用该值作为 `ctx.actor`；`packages/shared/src/index.ts:3668-3687` 只校验 `actor === currentAssignee`，不校验 actor 是否等于会话用户。
- 复现（scratch）：
  1. admin 建审批 `POST /api/approvals {"title":"audit-approval","type":"leave","applicantId":"audit_admin","currentAssignee":"boss"}` → 201，`POST .../submit {"actor":"audit_admin"}` → status=pending。
  2. 普通 user（role=user）`POST /api/approvals/1/approve {"actor":"boss"}` → **200，status=approved**。
- 建议修法：路由层从 `req.auth.user` 派生 actor（username 与 `members.user_id` 绑定），忽略/拒绝 body 中的 actor；shared 决策函数增加 `sessionUserId` 与 assignee 的映射校验；补断言：非 assignee 即使伪造 actor 也必须 403。

#### P1-2 · 备份导出/恢复无管理员闸门，普通用户可全量外泄并替换工作区

- 证据：`server.ts:4672-4680`、`4704-4738` 零 `assertPermission`；对比 `:3719/:3730/:3747` 仅用户管理和模式切换有 admin 校验；`backup.ts:14` 确认令牌是公开常量，只防误点、不防越权。
- 复现（scratch）：普通 user token `GET /api/backup/export` → **200，38 张业务表全量 JSON**；`POST /api/backup/restore` → **200 `restoredTables=38`**。
- 建议修法：export/validate/restore 三路由统一加 admin（或 `backup:read`/`backup:write`）权限；确认令牌升级为服务端一次性 nonce（与会话绑定）；补 HTTP 断言 user 调三个端点 → 403。

#### P2-2 · 匿名 `/api/settings`、`/api/health` 回显订阅 key 与 server.mode

- 证据：`server.ts:396-400` 两路径公开；`:515-517` 返回 `listSettings()` 全量；`:507-512` health 也带 settings；`:520-525` 把日历订阅 key 存进 settings；`packages/db/src/index.ts:379-382` 返回 key/value。
- scratch 实测：匿名 `GET /api/settings` → 200，admin 生成 key 后匿名再 GET 直接包含 `calendar_feed_key` 的值；但匿名 `GET /api/feeds/<key>.ics` 仍 401（remote 中间件生效），故仅为信息泄漏、不构成订阅越权。
- 建议修法：settings 公开端点只返回白名单键（如 `server.mode`），health 不回显 settings 明细。

#### P2-3 · 物资流水 `operator` 可客户端声明，审计归属可伪造

- 证据：`server.ts:3518-3526`，`operator` 取 `body.operator`（或 body memberId 对应的姓名），未与 `req.auth.user` 绑定；无授权判断，仅影响审计记载。
- 建议修法：与 P1-1 同法从会话派生操作人。
