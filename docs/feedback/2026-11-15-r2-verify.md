## 八、发现的问题

- **P1（发版前必修 · 一行级改动）** `scripts/shot.ps1:36` 分离启动 api 用 `pnpm dev:api`（tsx **watch**）。实测 3 次冷启动中 1 次成功 2 次失败：失败时日志打印 `[api] listening` 后 server 子进程静默消失（tsx watcher 孤儿存活但无子进程、端口未监听），`up` 60s 超时抛错——**间歇性不自持，r1 P1 的残留变体**。对照证据：audit-http.ps1:32 用 `pnpm exec tsx apps/api/src/server.ts`（非 watch）+ `< NUL`，本人在同机以同命令后台托管实测 **15s/35s/45s+ 存活、健康探针连续正常**——修复方向就是把 shot.ps1 的 api 启动换成 audit-http.ps1 同款（非 watch 或等价兜底），并把 `up` 的 ready 判定从「端口通」升级为「GET /api/health 200」（start.ps1 已是后者，所以 start.ps1 start 实测两轮成功）。README 快速开始主推的 `start.ps1 start` 因 start.ps1:35 先调 `shot.ps1 up`，在 up 抛错时会整链失败（本次实测 EXITCODE=1），同受此 bug 牵连。
- **P2（发版硬前置 · 非研发项，lead 收尾）** 任务单验收标准 3「发版 v0.0.2」未执行：package.json 仍 0.0.1、无 v0.0.2 tag。按宪法第二条属 VERDICT 通过后的 lead 动作，不构成研发打回，但**必须先修 P1 再发版**（发布前全量测试须绿，且 v0.0.2 的 start.cmd 用户路径不应带间歇性起不来的已知缺陷）。
