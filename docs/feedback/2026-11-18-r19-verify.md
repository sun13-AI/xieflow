## 二、阻断项

### P2（发版硬前置）：`GET /api/sync/status` 的 `lastChangeId/lastChangeAt` 取的是**最早**变更，不是最新变更

**现象（最小复现，本人实跑）**：fresh scratch DB 上依次 apply 两次（v1 create、v2 update）：
```
GET /api/sync/status
{"versions":[{...,"version":2}],"total":1,"lastChangeId":1,
 "lastChangeAt":"<v1 的时间>","schemaVersion":15}
```
即写了 2 条变更、当前版本 2，却回 `lastChangeId=1`。真实链路复现更强：6 条变更（直读库 `change_log` id=1..6、max=6）时 status 仍回 `lastChangeId=1`、`lastChangeAt` 为 id=1 的时间。

**根因**：`apps/api/src/server.ts:2752` 用 `store.listChanges(0, 1)` 取“最新”；而 `packages/db/src/index.ts:2483` 的 `listChanges` 是 `WHERE id > ? ORDER BY id ASC LIMIT ?`，`since=0&limit=1` 命中 **id 最小**的那条。应取 `ORDER BY id DESC LIMIT 1`（或复用已有的按实体最新查询扩展为全表最新）。

**用户影响**：`apps/web/src/SyncCard.tsx:83/89/163` 把 `sd.lastChangeAt` 直接显示为「最近同步」。CDP 真点实测：最后写入发生在 22:19:38，页面 reload 后仍显示「最近同步：2026/11/18 22:19:11」（首条 v1 时间）——用户越同步，这个时间越落后。

**为何全量测试没抓住**：`scripts/audit-http.ts:2635` 断言是 `ok(st1.json.lastChangeId > 0, "status 回带最后变更 id")`，标签写「最后变更 id」但实际只验 `> 0`，返回 1（首条）也通过；e2e 无对应精确断言。建议修复同时把该断言改成写入 v2 后 `eq(lastChangeId, 实际 v2 的 applied.id)` 与 `eq(lastChangeAt, v2.createdAt)`，否则回归仍会漏。

**可执行返工项**：① `server.ts` 的 status 改取真正最新一条（新增 db 只读 helper 或 `ORDER BY id DESC LIMIT 1`）；② `audit-http.ts` 把 `> 0` 弱断言换成精确等值断言（含 v3 后再查一次）；③ 重跑 `pnpm run test:all` 必须 1712/1439 全绿（若新增断言则只涨不缩并同步 README）；④ 真点复核「最近同步」随时间前进。此项修复后我可立即复验。
