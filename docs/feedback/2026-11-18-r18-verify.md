## 四、问题分级

### P1（发版前必修）：远端模式登录后业务页仍全部 401，且业务 401 不清假登录态、不跳登录页

- **影响**：r18 目标「从本地单机走向网络版」在 UI 侧不成立。用户登录后点「待办」等任一业务 tab 都得到「加载失败 / 登录态无效或已过期」；同时业务路由返回的 `cleared=true` + `X-Xieflow-Auth-Cleared:1` 被前端忽略，localStorage 里假 token 不会被清除，违背任务单「401 清假登录态（r1 教训）」与验收标准 3「模式切换后 UI 状态正确」。
- **根因定位（可验证）**：`apps/web/src/authClient.ts:59-70` 的 `apiFetch` 确实会在 401 时 `clearSession()` + `goToLogin("401")`，但它只被 `App.tsx:208,226`（模式切换/登出）调用；业务页全部用裸 `fetch`：`App.tsx:64-66`（fetchHealth 的 schedules/todos）、`TodosPage.tsx:36`、`AssetsPage.tsx:23,27`、`KnowledgePage.tsx:47,51`、`DocsPage.tsx:120`、`MindmapPage.tsx:28,32`、`ApprovalPage.tsx:51,55`、`WhiteboardPage.tsx:35,39`、`BasesPage.tsx:100`、`ChatPage.tsx:58-59` 等。裸 fetch 不带 `Authorization`，也不读 `cleared` 响应。HTTP audit 之所以全绿，是因为它直接构造 Bearer 头验服务端，没覆盖浏览器发请求这一层。
- **可执行修法**：把上述页面级请求统一改走一个带 `readToken()` 注入 `Authorization: Bearer …` 的 fetch 包装（可直接复用 `apiFetch`，或安装等价的全局 fetch interceptor），并在响应为 401（或头 `X-Xieflow-Auth-Cleared=1`）时统一 `clearSession()` + `goToLogin("401")`；`fetchHealth` 的 401 也必须走同一入口，不能继续静默降级为空态。
- **验证口径**：修后 headless 重跑第三节 0–6：remote 真登录 → 点「待办」/「物资」/「文档」至少 3 个业务 tab 返回 200 且渲染真实空态/数据；注入假 token → 业务 401 后 URL 自动变 `?page=login&reason=401` 且 localStorage token=null；`pnpm run test:all` 断言数不低于 1625/1369。建议在 audit-http 之外补一条 headless CDP 断言锁住该浏览器层行为，避免再次只测服务端。
