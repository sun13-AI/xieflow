## 一、N+1 查询审计

### 扫描命令与命中数（在仓库根执行）

```bash
rg -n 'this\.db\.(get|all)\(' packages/db/src/index.ts
# 121 行命中；文件共 3815 行 / 158654 字节

rg -n '\.map\(\(.*\) => this\.|for \(const .* of .*\)|forEach' packages/db/src/index.ts
# 33 行；逐条甄别后「读路径循环内逐条单查询」= 2 处（listForms / listBoardCards*）
```

逐条甄别结论：`this.db.get/all` 的 121 处中，绝大多数是**单行读回**（insert 后用 lastInsertRowid 回读）、守卫查询（COUNT / 唯一性）、或 `SELECT * FROM ...` 一次性 `all`。真正构成 N+1 的只有下表 2 处。

### 实测方法

- `openDatabaseRaw({path: scratch})` 后包裹 raw 句柄的 `get/all` 计数（TS `private` 运行期可见），精确统计每次服务调用的 SQL 次数。
- 100 / 500 / 1000 三档**各自全新 scratch DB**，每档真造同量级的 todos / documents / records / forms（每 form 2 题）/ cards（每卡 2 标签）后测；非累积。
- 同时用真 HTTP（scratch api :18788，local 模式）测路由层耗时（5 次取中位数）。

## 二、大列表渲染审计

### 是否有分页/虚拟化（static）

- 表格页：`apps/web/src/BasesPage.tsx:163/585/631/716/750` 各处 `pageSize: 20`；服务端 `packages/shared/src/index.ts:1158-1159` `DEFAULT_PAGE_SIZE=20 / MAX_PAGE_SIZE=100`，`:1270-1282` 真切片 + total。**实测每页仅 20 行 / DOM 527 节点**，机制生效。
- 待办页 `apps/web/src/TodosPage.tsx`、文档页 `apps/web/src/DocsPage.tsx`：grep `pageSize|slice\(|virtual` **0 命中**；全量渲染。

### 实测方法

scratch DB 造 1000 todos / 1000 documents / 1000 table records → api :8787（local）+ vite :5173（`--host 127.0.0.1`）→ headless Edge CDP `Page.addScriptToEvaluateOnNewDocument` 注入 `performance.now()` 起点 + rAF 轮询目标选择器，导航到 `?page=todos|bases|docs`；读取 `firstRenderMs = 目标行出现时刻 - 文档开始`、`document.querySelectorAll('*').length`、行数。

### 实测数据表（条数 × 首次渲染 × DOM 节点 × 行数）

| 页面 | 条数 | 首次渲染（冷，多次） | DOM 节点数 | 渲染行数 |
|---|---|---|---|---|
| 待办 `?page=todos` | 1000 | 1532.8 / 1674.9 / 1685.4 / **2077.4** ms（4 次） | **9092** | 1000 |
| 待办（同会话热导航 3 次） | 1000 | 419.6 / 412.0 / 458.0 ms | 9092 | 1000 |
| 待办 `?page=todos` | 500 | 314.4 / 322.8 / 335.1 ms | 4592 | 500 |
| 表格 `?page=bases` | 1000（服务端分页） | 257.9 / 285.6 ms | 527 | **20** |
| 文档 `?page=docs` | 1000 | 280.8 / 299.9 ms | 4099 | 1000 |

阈值对照：>2s 或 DOM>10000 记真问题。
- 表格页：**零问题**（分页机制 + 实测 20 行 / 527 节点 / 0.26s）。
- 文档页：**零问题**（1000 行 0.28s / 4099 节点）。
- 待办页：冷启动 4 次中 1 次 2077ms 越线，其余 1.53–1.69s；热导航 0.41–0.46s；DOM 9092 逼近阈值。**严格按「>2s 或 >10000」仅 1/4 冷启动越线，判 P2 记账（无分页/虚拟化，节点随条数线性增长，~1100 条即破 10000）**，不是稳定 P1。

**结论（大列表）：表格/文档零问题；待办页无分页/虚拟化为 P2 记账。**

## 四、大内存审计（r49 备份 / r33 搜索 / 上限保护）

### r49 `GET /api/backup/export`（38 表 JSON 全量快照）

| 条数 | 响应字节 | 耗时（中位数） | SQL 次数 | 表数 |
|---|---|---|---|---|
| 100 | 120,977 B | 25.1 ms | 38（常量） | 38 |
| 500 | 595,378 B | 42.5 ms | 38 | 38 |
| 1000 | **1,193,398 B（1.14 MiB）** | **53.3 ms** | 38 | 38 |

- 机制：`packages/db/src/index.ts:652-663` `exportBackupSnapshot()` 对 `BACKUP_TABLES` 38 张表各 1 次 `SELECT *`，`apps/api/src/server.ts:4767-4777` 一次性 `buildBackupFile` + `reply.send(backup)` ——**全量内存构建，无流式**。
- 判定：1000 条下 1.14 MiB / 53ms，无问题；但无响应体大小上限、无流式，数据再增一个数量级会线性涨内存。**P2 记账（保护性观察）**。
- 上限保护：无（设计上备份要求完整性，不做截断）。

### r33 `GET /api/search`（跨八源全表扫描）

| 条数（每源） | `?q=audit` 命中耗时 | `?q=zzzznotfound` 零命中耗时 | 响应字节 |
|---|---|---|---|
| 100 | 81.7 ms | 70.4 ms | 2,426 B |
| 500 | 352.1 ms | 336.7 ms | 2,426 B |
| 1000 | **667.8 ms** | **656.0 ms** | 2,447 B |

- 机制：`apps/api/src/server.ts:285-363` `collectSearchSources` 对 8 源各调 `list*()`（全表 `SELECT *`）在内存装配候选；`packages/shared/src/globalSearch.ts:241-294` 打分/去重/截断。零命中耗时与命中几乎相同 → **证明是全表扫描，与匹配数无关**。
- 上限保护：`globalSearch.ts:64-66` `DEFAULT_SEARCH_LIMIT=20 / MAX_SEARCH_LIMIT=50 / DEFAULT_SEARCH_PER_SOURCE=5`；`:108-115` limit 1~50 越界 400；`:277-292` 每源 top-5 + 全局 top-N。**输出有上限（防大源淹没/防巨响应），扫描无上限（O(总行数)）**。
- 判定：1000 条下 0.67s 偏慢但未越 2s；输出恒定 ~2.4KB 有上限。**P2 记账（扫描线性、无 FTS/无提前终止）**，非当前规模真问题。

### r32 文档导出（顺带核对）

`GET /api/documents/:id/export.html` 走 shared `blocksToPrintHtml`，单文档单块集，无跨表 N+1；本轮未造超大单文档（1000 文档各默认块），不记真问题。

**结论（大内存）：1000 条下备份 1.14 MiB / 53ms、搜索 0.67s / 2.4KB，均未越阈值；输出上限存在、扫描无上限，两项 P2 记账。**
