## 三 · 危险区证据（本轮重点）

1. **白名单最小化**：`BACKUP_TABLES` 只有 38 张业务表；`BACKUP_RUNTIME_TABLES = ["sessions","change_log","entity_versions","users"]` 明确排除。
   - `users` 一并排除的工程理由：`sessions.user_id` 是 `ON DELETE CASCADE` 外键，若恢复时清空 users 会连带删除会话——直接违反「不动 sessions」红线；账户 `password_hash` 也不随业务快照漂移。
   - e2e 三条断言分别锁 sessions / change_log / users / entity_versions 不在白名单；导出快照键数与白名单表数严格相等；audit 导出响应四个键均 undefined。
2. **恢复前预览清晰**：`/validate` 只返回清单与逐表行数、零写入；web 必须在对话框勾选确认后按钮才启用；对话框明示「整体替换 38 张业务表、不可撤销」与确认口令。
3. **零半态双保险**：`planRestore` 校验失败 → `steps=[]`；db 层 `BEGIN IMMEDIATE` → 反序 DELETE + 正序 INSERT → 任一 SQL 失败 `ROLLBACK`。
   - e2e：注入 `quadrant=q9` 的 CHECK 违规行 → 抛错且 38 表 JSON 快照逐字节不变；audit：同一语义真 HTTP 400 + `RESTORE_ROLLED_BACK` + 待办表逐字节不变。
4. **用户数据不误删**：唯一删除发生在白名单表内、且由用户显式确认；非白名单表无任何 DELETE SQL（db 层 SQL 由常量拼接，e2e 锁 `applyBackupPlan` 拒绝表集合越界的快照）。
5. **数据源隔离**：截图与 CDP 全走 `scripts/.tmp-r49*/` scratch 库并删除；仓库 `data/xieflow.db` 未作数据源。
